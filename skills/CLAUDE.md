# Skills

Slash-command skills for Claude Code. Each subdirectory is one skill with a `SKILL.md` (YAML frontmatter — `name`, `description`, `argument-hint`, `allowed-tools`, plus `user-invocable: false` + `disable-model-invocation: true` for reference-only skills — followed by the workflow prose). Claude Code loads these from `~/.claude/skills/`; editing a file here goes live only after re-running the plugin install or copying the folder into `~/.claude/`.

A **git** pre-commit hook (distinct from the plugin hooks in `hooks/`) runs `scripts/sync-workflows.sh`, which regenerates `.devin/workflows/*.md` (gitignored) from every `SKILL.md` here — except reference-only skills (`user-invocable: false`), which are skipped.

`issue-log/` is one such reference skill: it holds the issue-log stamp spec (envelope, event registry, shared rules) that the workflow skills' stamp blocks link to. When touching any stamp block, change shared rules only in the spec.

`glossary/` is the second reference skill: it owns the personal glossary at `~/.claude/glossary.md` — entry format and caps, reading rules, dedupe, creation, backup, the write protocol, shell-sourced dates, the Leitner ladder, and quiet mode. Six writers cite it and restate none of it: `term-add/` (standalone capture), `term-quiz/` (spaced-repetition state), and the four walks — `brainstorm-walk/`, `blueprint-walk/`, `test-plan-walk/`, and `review-walk/` — each of which routes `add term` through `term-add/` in quiet mode. A format change belongs in the spec, never in a writer. Unlike the rest of the repo, `term-add/` and `term-quiz/` are repo-independent and post no issue stamps.

The planning skill is `blueprint/` (with `blueprint-deepen/` as its second-pass counterpart) — named to avoid colliding with Claude Code's built-in plan mode. The artifact it writes is still called a plan and still lands in `docs/plans/`; only the invocation was renamed.

**Naming: producers versus consumers.** A skill's name is decided by whether it makes an artifact or acts on one that already exists.

- **Producers are named for what they produce.** They create an artifact that did not exist before, so there is nothing for an `<artifact>-<action>` name to bind to. Current producers: `brainstorm/`, `blueprint/`, `work/`, `deep-review/`, `quick-review/`, `compact-prep/`, `test-plan/`, `compound/`, `deprecate/`, `initiative/`.
- **Consumers are named `<artifact>-<action>`.** They act on an artifact that is already on disk, so the artifact leads and the verb follows. Current consumers: `brainstorm-walk/`, `blueprint-walk/`, `blueprint-deepen/`, `test-plan-walk/`, `test-plan-run/`, `review-walk/`, `review-sweep/`, `review-push/`.

A skill that both authors an artifact and later resumes it — `initiative/` is the only current one — is named for the artifact it **authors**, since that is the mode that brings the doc into existence. The resume mode does not earn a second, consumer-shaped name.

Two consequences worth stating, because both look like exceptions and neither is. `deep-review/` and `quick-review/` are *correct* under this rule rather than grandfathered — they are producers, so they are named for the review they write, and the adjective goes in front; `review-quick` would be wrong, because it reads as an action on an existing review doc, which is exactly what the eight consumers do. And `review/` alone is unavailable regardless: it collides with a Claude Code built-in, the same collision that forced `/plan` → `/blueprint` (see `## Related`, PR #61).

The rule covers skills that read or write a `docs/` artifact. Skills whose object is a branch, a PR, a worktree, or an issue — `ship/`, `land/`, `tree/`, `read-issue/`, `triage-issue/` — are outside it and were not renamed to fit.

`walk-protocol/` is the third reference skill: it owns every rule the four walks share — walk order and the no-batching rule, resume, the self-loop contract, the edit-anchoring and re-read discipline, claim-first, the destructive-action gate, the term-capture side buffer, and the summary-and-stamp shape. The walks cite it and restate none of it; a rule that drifts between four files is worse than a rule stated once.

`review-protocol/` is the fourth reference skill: it owns every rule the two reviews share — review-target resolution, the protected-artifacts list, the raw-findings scratch contract, the synthesizer dispatch and its count sanity-check, review-document verification and the inline fallback, the completion report and next-steps block, and the `review-written` stamp's shared body. `deep-review/` and `quick-review/` cite it and restate none of it, embedding only what differs by depth — which agents run and how they are selected, how much thinking each phase gets, their own working-tree policy, their own `Review Agents Used` list, their own filled stamp template, and whatever they offer after the report. It deliberately does **not** own the review-document format: that belongs to `agents/review/review-synthesizer.md`, which writes the doc, and both reviews produce it identically so `review-walk/`, `review-sweep/`, and `review-push/` consume either one unchanged.

`test-protocol/` is the fifth reference skill: it owns every rule the four test callers share — the fixed roster and what each lens may see, the surface digest, the tag vocabulary, the keep and drop rules, the Drop List and the revise bucket, the scratch contract, the synthesizer dispatch and its count check, document verification and the document format, the assurance filters and re-run semantics, presenting a case, the receipts, the completion report, and the `test-plan-written` and `tests-run` stamps' shared bodies. `test-plan/`, `test-plan-walk/`, `test-plan-run/`, and `grind/`'s test plan cite it and restate none of it, embedding only their own prose — origin discovery, how each builds the digest, the lens briefs, argument parsing, each filled stamp template, and each terminal wording. Two divergences from `review-protocol/` are deliberate. It **does** own the document format, because no single agent writes the whole document: the synthesizer writes the cases and `test-plan-walk/` and `test-plan-run/` write back into them, so a format owned by an agent would drift. And it owns the **roster**, because the roster is fixed and identical for every caller rather than varying by depth — that is the rule that makes "grind's test plan never re-enumerates the lenses" enforceable. Grind is a producer only, like `test-plan/`: it writes the document and stops, so the writer and the assurance filters run only under `test-plan-run/`. Its scope stops at the test family: nothing in `work/` depends on a test plan existing — the only link is one-way, the blast-radius lens reading a work doc's `## Tests to Revisit` per `work-protocol/` — `blueprint/` prescribes no tests, and a branch that is never test-planned ships exactly as it does today.

`work-protocol/` is the sixth reference skill: it owns the work document `work/` and `grind/` write to `docs/work/` while they build — the filename and frontmatter, the four sections (Changes, Tests to Revisit, Decisions, Deviations), the `D1`/`D2`/`D3` card and its `Status:` vocabulary, the `forge:workflow:scope-observer` dispatch contract in its two modes and the visibility wall that keeps the worker's own account from the observer, the observed marker and resume, the reply verbs, and the terminal one-liners. `work/` (one doc per run, cards resolved by a one-line reply) and `grind/` (one doc per run, built slice by slice, every card left `open`) cite it and restate none of it. The test callers read only its `## Tests to Revisit`, through the blast-radius lens, and a work doc never reads a test or review doc. Like `test-protocol/`, it owns its document format, because the orchestrator writes the doc from several sources — git, the worker's return, the observer's cards — and no single agent owns it.

The walks are a family of four, one per artifact: `brainstorm-walk/` over a requirements doc, `blueprint-walk/` over a plan, `test-plan-walk/` over a test plan, `review-walk/` over a review doc. Each is an interactive, resumable walk that records its verdicts inline in the document it reads (`**Reviewed:**` per unit or requirement, the same live-in-the-doc idea as review-walk's `Status:` — though the field name and vocabulary differ, because a requirement or unit is being judged while a review finding is being remediated; `test-plan-walk/` writes `**Walk:**` keep-or-cut per case), each is optional, and each reads-then-edits its doc in place, so two rules are load-bearing across all four — they never renumber (`remove` tombstones at the existing ordinal, marked `retired`, because doc text and issue stamps cite units and requirements by number), and neither `modify` nor `remove` writes without a before/after confirm — `docs/` is gitignored and the walks keep no backup, so that confirm is the only guard. `test-plan-walk/` has no `modify` or `remove`, and a cut keeps the case block where it is, so both rules hold for it without a confirm. The `add term` side buffer is the one piece of state they keep outside the repo — but the file, its format, and the write all belong to `glossary/` and `term-add/`; a walk only asks for the term and shows the one confirmation line back. Nothing depends on a doc having been walked, with two exceptions: `blueprint/` honors a `**Reviewed:** retired` requirement by excluding it, since retiring is a deliberate withdrawal and re-planning it would undo the human's decision, and `test-plan-run/` never runs a `cut` case, for the same reason. Otherwise walked and unwalked docs read identically — `work/` and `grind/` treat plans that way in every case, and `grind/` invokes no walk.

`brainstorm-walk/` diverges from its three siblings in two places. First, a requirements doc whose bullets carry no `R`-IDs is a **hard stop** with an actionable message, not a degraded read-only walk: an unnumbered requirements doc is a current-shape artifact one edit from being walkable, whereas the old-shape plan `blueprint-walk/` degrades for will never be regenerated, so offering a consolation walk here would hide the one-line fix. Second, its `**Reviewed:**` state lives on a two-space-indented continuation line *inside the `R`-bullet's own list item* rather than under a heading — an `- Rn.` bullet has no body, and an unindented state line would terminate the list and orphan every requirement below it.

The reviews are a family of two, one per depth over the same diff: `deep-review/` with a configurable roster plus conditional agents, `quick-review/` with a fixed roster of two-or-three. Depth is the only axis they differ on — same spec, same synthesizer, same document — so the three consumers never branch on which one wrote the doc. Two divergences are deliberate and load-bearing. `quick-review/`'s roster is not read from `cc-forge.local.md` and is never padded to three: it picks at most one language reviewer by the diff's dominant extension — **dominance counted in files changed, not lines**, so one vendored or generated blob can't pull the wrong reviewer — and when nothing matches, two agents ran and the terminal report says so. And it never arranges the working tree: it reviews the branch checked out in the current directory, creating no worktree and switching no branch, so a target that isn't checked out here is a stop with a `/tree` suggestion rather than a checkout. Isolation is `deep-review/`'s behavior, not a precondition for reviewing.

`review-sweep/` is the unattended sibling of `review-walk/` over the same doc: same auto-discovery, same `Status:` vocabulary, no prompts. It adds one field of its own — a `**Sweep:** <reason>` line directly under `Status:` on every finding it decides: a fixed-vocabulary reason on the ones it leaves `open`, so the surfaced set reads as a worklist rather than prose, and `implemented — <what changed>` on the ones it lands, so the line doubles as the sweep's signature (`grind/` signs its triage with a `Grind:` line the same way; `review-walk/` writes neither, so a verdict carrying no signature was the user's); `review-walk/` renders that line, and `review-push/` captures only the fields it names and so passes over it, leaving both able to consume a swept doc unchanged. It is the conservative inverse of `grind/`'s accept-by-default triage: the two share the read-the-code-before-any-verdict rule, but grind implements unless a finding is rejected while the sweep surfaces unless a finding is cheap and certain. Two guardrails bound what it will land unattended: a **sensitive-path** check (condition 8, defined in `review-sweep/SKILL.md` and sweep-only — `grind/` has no counterpart) surfaces any finding citing a migration, CI-workflow, or infra-config path **unread**, and medium-confidence findings are implemented only at P1 or P2. `Skip reason:` codes are `review-walk/`'s, shared by all three writers, so they stay countable across docs. It runs **no tests** — verifying its edits is the user's next step. It edits inline and leaves everything uncommitted — no commits, no pushes, no issues — so what it did is a `git diff` away.

Two execution paths run a plan. `work/` → `test-plan/` → [`test-plan-walk/`] → `test-plan-run/` → `ship/` are confirm-gated (each stops for user approval), and `land/` finishes the chain click-free: CI is the only gate (local suite only for no-CI repos), red halts rather than triggering fix commits, and it never pushes a commit. The suite runs **once**, in CI, off `ship/`'s push — `work/` runs no suite, `test-plan-run/` runs only the tests it just wrote, through the assurance filters, and `ship/`'s pre-merge checklist holds only what CI cannot run. `grind/` is the autonomous counterpart up to an open PR — it confirms one phase's slices once, then builds every slice on one branch, reviews the whole branch once, triages, fixes, writes one test plan, and opens a ready PR without prompting. It never watches CI and never merges: the user picks up in a new session in the worktree with `review-walk/` → `review-push/` → `test-plan-walk/` → `test-plan-run/` → `ship/` → `land/`. It deliberately does **not** call the other skills (their approval gates would deadlock it; merging is the user's); instead it mirrors their processes — `work/`'s per-unit commit+stamp cadence and work doc (one per run, per `work-protocol/`), `deep-review/`'s roster (minus `test-coverage-reviewer`) and synthesizer, `test-plan/`'s lenses and synthesizer, `ship/`'s PR shape — so a grind run's issue thread reads like a manual run's.
