# Skills

Slash-command skills for Claude Code. Each subdirectory is one skill with a `SKILL.md` (YAML frontmatter — `name`, `description`, `argument-hint`, `allowed-tools`, plus `user-invocable: false` + `disable-model-invocation: true` for reference-only skills — followed by the workflow prose). Claude Code loads these from `~/.claude/skills/`; editing a file here goes live only after re-running the plugin install or copying the folder into `~/.claude/`.

A pre-commit hook runs `scripts/sync-workflows.sh`, which regenerates `.devin/workflows/*.md` (gitignored) from every `SKILL.md` here — except reference-only skills (`user-invocable: false`), which are skipped.

`issue-log/` is one such reference skill: it holds the issue-log stamp spec (envelope, event registry, shared rules) that the workflow skills' stamp blocks link to. When touching any stamp block, change shared rules only in the spec.

`glossary/` is the second reference skill: it owns the personal glossary at `~/.claude/glossary.md` — entry format and caps, reading rules, dedupe, creation, backup, the write protocol, shell-sourced dates, the Leitner ladder, and quiet mode. Five writers cite it and restate none of it: `term-add/` (standalone capture), `term-quiz/` (spaced-repetition state), and the three walks — `brainstorm-walk/`, `blueprint-walk/`, and `review-walk/` — each of which routes `add term` through `term-add/` in quiet mode. A format change belongs in the spec, never in a writer. Unlike the rest of the repo, `term-add/` and `term-quiz/` are repo-independent and post no issue stamps.

The planning skill is `blueprint/` (with `blueprint-deepen/` as its second-pass counterpart) — named to avoid colliding with Claude Code's built-in plan mode. The artifact it writes is still called a plan and still lands in `docs/plans/`; only the invocation was renamed.

`walk-protocol/` is the third reference skill: it owns every rule the three walks share — walk order and the no-batching rule, resume, the self-loop contract, the edit-anchoring and re-read discipline, claim-first, the destructive-action gate, the term-capture side buffer, and the summary-and-stamp shape. The walks cite it and restate none of it; a rule that drifts between three files is worse than a rule stated once.

The walks are a family of three, one per artifact: `brainstorm-walk/` over a requirements doc, `blueprint-walk/` over a plan, `review-walk/` over a review doc. Each is an interactive, resumable walk that records its verdicts inline in the document it reads (`**Reviewed:**` per unit or requirement, the same live-in-the-doc idea as review-walk's `Status:` — though the field name and vocabulary differ, because a requirement or unit is being judged while a review finding is being remediated), each is optional, and each reads-then-edits its doc in place, so two rules are load-bearing across all three — they never renumber (`remove` tombstones at the existing ordinal, marked `retired`, because doc text and issue stamps cite units and requirements by number), and neither `modify` nor `remove` writes without a before/after confirm — `docs/` is gitignored and the walks keep no backup, so that confirm is the only guard. The `add term` side buffer is the one piece of state they keep outside the repo — but the file, its format, and the write all belong to `glossary/` and `term-add/`; a walk only asks for the term and shows the one confirmation line back. Nothing depends on a doc having been walked, with one exception: `blueprint/` honors a `**Reviewed:** retired` requirement by excluding it, since retiring is a deliberate withdrawal and re-planning it would undo the human's decision. Otherwise walked and unwalked docs read identically — `work/` and `grind/` treat plans that way in every case, and `grind/` invokes no walk.

`brainstorm-walk/` diverges from its two siblings in two places. First, a requirements doc whose bullets carry no `R`-IDs is a **hard stop** with an actionable message, not a degraded read-only walk: an unnumbered requirements doc is a current-shape artifact one edit from being walkable, whereas the old-shape plan `blueprint-walk/` degrades for will never be regenerated, so offering a consolation walk here would hide the one-line fix. Second, its `**Reviewed:**` state lives on a two-space-indented continuation line *inside the `R`-bullet's own list item* rather than under a heading — an `- Rn.` bullet has no body, and an unindented state line would terminate the list and orphan every requirement below it.

`review-sweep/` is the unattended sibling of `review-walk/` over the same doc: same auto-discovery, same `Status:` vocabulary, no prompts. It adds one field of its own — a `**Sweep:** <reason>` line directly under `Status:` on every finding it leaves `open` — drawn from a fixed reason vocabulary so the surfaced set reads as a worklist rather than prose; `review-walk/` renders that line, and `push-review/` captures only the fields it names and so passes over it, leaving both able to consume a swept doc unchanged. It is the conservative inverse of `grind/`'s accept-by-default triage: the two share the read-the-code-before-any-verdict rule, but grind implements unless a finding is rejected while the sweep surfaces unless a finding is cheap and certain. It edits inline and leaves everything uncommitted — no commits, no pushes, no issues — so what it did is a `git diff` away.

Two execution paths run a plan to merged code. `work/` → `ship/` are confirm-gated (each stops for user approval), and `land/` finishes the chain click-free: CI is the only gate (local suite only for no-CI repos), red halts rather than triggering fix commits, and it never pushes a commit. `grind/` is the autonomous counterpart — it confirms a PR breakdown once, then builds, reviews, triages, fixes, and merges each slice without prompting. It deliberately does **not** call the other skills (work/ship's approval gates would deadlock it; land is per-PR and human-invoked); instead it mirrors their processes — `work/`'s per-unit commit+stamp cadence, `deep-review/`'s roster and synthesizer, `push-review/`'s outcome comment, `ship/`'s PR shape, `land/`'s merge posture — so a grind run's issue thread and PR history read identically to a manual run's. `land/` and `grind/`'s merge phases are aligned by design (issue #66 landed the alignment); changes to either should keep the two matched.
